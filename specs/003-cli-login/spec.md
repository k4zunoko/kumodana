# Feature Specification: kumo CLI にブラウザでログインする（kumo login / logout）

**Feature Branch**: `003-cli-login`

**Created**: 2026-10-20

**Status**: Draft

**Input**: User description: "kumo CLI に kumo login と kumo logout を加え、ブラウザで所有者としてログインするだけで CLI を使えるようにする（Cloudflare Access の Managed OAuth）。CLI 用サービストークンのシークレットを PC に配らずに済むようにする"

**関連**: Issue #3（全体）、#5（この仕様）、#4（本番での検証）、後続の #6〜#10、憲法 v2.1.0。
この仕様は、001 の [contracts/cli.md](../001-share-shelf-mvp/contracts/cli.md) の「設定」と、
[contracts/admin-api.md](../001-share-shelf-mvp/contracts/admin-api.md) の「認証（2 段）」の 1 段目に、ブラウザでのログインの経路を加える。
001 の FR-031（所有者のメールアドレスによるログイン）と FR-033（資格情報を出力に表示しない）の範囲に収まる。

## 用語

- **ログイン**: 所有者がブラウザで、管理用のサービスの入口（Access）に所有者のアカウントで入ること。ブラウザで管理 API を開くときと同じログインを使う。
- **許可**: 1 回のログインで、この PC の kumo CLI に与えられる管理操作の権利。期間（**許可の期間**）があり、途中で取り消せる。
- **アクセストークン**: 管理 API に送る、短い期限の資格情報。期限が切れたら、リフレッシュトークンで取り直す（更新する）。
- **リフレッシュトークン**: 許可が続くあいだ、アクセストークンを取り直すための資格情報。
- **ログインの記録**: この PC に保存する、ログインした管理 API の URL、この PC の登録情報、アクセストークンとその期限、リフレッシュトークン、ログインした日時。
- **サービストークン**: 今の CLI が使っている、Access が発行したクライアント ID とシークレットの組。環境変数か設定ファイルに書く。

## Clarifications

### Session 2026-10-20

- Q: 許可の期間とアクセストークンの期間を、どの値にするか → A: アクセストークン 15 分（既定）、許可 1 週間。1 週間が管理画面の選択肢になければ、
  1 週間以下でいちばん長い値にする。選択肢はまだ確かめていないので、実際の値は #9 で設定するときに確かめる
- Q: ログインの記録を、どこにどう保存するか → A: `config.json` と同じフォルダーの別のファイル `login.json` に平文で保存する。
  Windows 以外では権限を 600 にする。CLI が書き換えるのはこのファイルだけで、`config.json` は書き換えない
- Q: ログインの状態を表示する手段を、どの形で作るか → A: `kumo login --status`。通信せずに、保存した記録と設定から表示する（JSON の出力にも対応）
- Q: 資格情報が複数あるとき、どの順で使うか → A: 環境変数のサービストークン → ログインの記録 → `config.json` のサービストークン。
  環境変数は、`KUMODANA_CLIENT_ID` と `KUMODANA_CLIENT_SECRET` のどちらか一方でも設定されていれば、今までどおりの経路を使う

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 新しい PC で、ブラウザでログインして使い始める (Priority: P1)

所有者は、新しい PC に kumo CLI を入れたら、管理 API の URL を指定してログインのコマンドを実行する。既定のブラウザが開き、
所有者のアカウントでログインすると、CLI がそれを受け取り、すぐに管理操作を使えるようになる。シークレットを持ち運んだり、
設定ファイルを手で書いたりする必要はない。

**Why this priority**: サービストークンのシークレットを PC に配る手間と危険（一度しか表示されない、2 台目の設定で 1 台目が使えなくなる）をなくすことが、この機能の目的そのものである。

**Independent Test**: 設定ファイルのない PC（または環境）で、CLI を入れてログインのコマンドを実行し、ブラウザで所有者としてログインして、
使用量の表示が成功することを確かめる。

**Acceptance Scenarios**:

1. **Given** 設定ファイルもログインの記録もない PC, **When** 所有者が `kumo login <管理 API の URL>` を実行し、開いたブラウザで所有者としてログインする,
   **Then** CLI はログインできたことと、管理 API で確かめた結果（使用量）を表示し、以後の管理操作が成功する
2. **Given** ブラウザを自動で開けない環境, **When** 所有者がログインのコマンドを実行する, **Then** 開くべき URL が表示され、
   所有者がその URL を同じ PC のブラウザで開いてログインすると、1 と同じ結果になる
3. **Given** ログインのコマンドが待っている, **When** 所有者がブラウザで所有者以外のアカウントでログインしようとする, **Then** 入口で拒否され、
   CLI は資格情報を何も保存しない
4. **Given** ログインのコマンドが待っている, **When** 所有者がブラウザで操作せずに上限の時間（5 分）が過ぎる、または中断する,
   **Then** CLI は時間切れか中断を表示して終わり、資格情報を何も保存しない
5. **Given** この PC で一度ログインしたことがある, **When** もう一度ログインする, **Then** この PC は登録し直されず、新しい許可に置き換わり、
   前の許可は取り消される

---

### User Story 2 - ログインしたまま、ブラウザを開かずに使い続ける (Priority: P2)

所有者は、許可の期間内であれば、ブラウザを開かずにすべての管理操作を使い続けられる。アクセストークンの期限が切れても、
CLI が自動で取り直す。許可の期間が切れたときや取り消されたときは、何をすればよいかが表示される。

**Why this priority**: 毎回ブラウザを開くのでは、今のサービストークンより不便になる。日々の使い勝手を保つために要る。

**Independent Test**: ログインした後、アクセストークンの期限をまたいで管理操作を続けて実行し、ブラウザを開かずにすべて成功することを確かめる。
次に許可を取り消し、管理操作で「ログインし直す」案内が出ることを確かめる。

**Acceptance Scenarios**:

1. **Given** ログイン済みで、アクセストークンの期限が切れている, **When** 所有者が管理操作を実行する, **Then** CLI はブラウザを開かずに
   アクセストークンを取り直して保存し、操作は成功する
2. **Given** ログイン済み, **When** 2 つの管理操作を同時に実行し、どちらもアクセストークンを取り直す, **Then** 両方とも成功する
3. **Given** 許可の期間が切れた、または管理画面や API で許可が取り消された, **When** 所有者が管理操作を実行する, **Then** 操作は失敗し、
   「`kumo login` を実行してください」と案内され、終了コードは `1` になる
4. **Given** ログイン済み, **When** どのコマンドを、他のツール向けの JSON の出力を含めて実行する, **Then** アクセストークン、リフレッシュトークン、
   ログインの途中で受け取る値は、どの出力にもエラーにも表示されない
5. **Given** 環境変数か設定ファイルにサービストークンを設定している PC, **When** ログインせずに管理操作を実行する, **Then** この機能の追加前と同じように成功する

---

### User Story 3 - ログアウトして、この PC の許可を無効にする (Priority: P3)

所有者は、PC を使わなくなるときや、記録が漏れたかもしれないときに、ログアウトのコマンドで、この PC の許可を取り消し、
保存した資格情報を消せる。

**Why this priority**: 許可を手放す手段がないと、使わなくなった PC に、期間が切れるまで有効な資格情報が残る。

**Independent Test**: ログインした PC でログアウトし、同じ PC で管理操作が「ログインし直す」案内で失敗すること、保存した資格情報が
消えていることを確かめる。

**Acceptance Scenarios**:

1. **Given** ログイン済み, **When** 所有者が `kumo logout` を実行する, **Then** この PC の許可が取り消され、アクセストークンとリフレッシュトークンが
   PC から消え、取り消した時点から、残っていたアクセストークンも使えなくなる。管理 API の URL とこの PC の登録情報は、次のログインのために残る
2. **Given** ログイン済みで、ネットワークにつながらない, **When** ログアウトする, **Then** 資格情報は PC から消え、許可を取り消せなかったことと、
   許可がまだ有効であること、取り消す方法が表示される。終了コードは `1` になる
3. **Given** 環境変数にサービストークンが設定されている, **When** ログアウトする, **Then** 今後もそのサービストークンが使われることが警告される
4. **Given** ログインの記録がない, **When** ログアウトする, **Then** ログインしていないことが表示され、成功（終了コード `0`）で終わる

---

### User Story 4 - ログインの状態を確かめる (Priority: P4)

所有者は、`kumo login --status` で、この PC の CLI がどの方法で管理 API に接続するのか（ログイン、サービストークン、未設定）と、
ログインしている場合はその状態（管理 API の URL、ログインした日時、アクセストークンの期限）を確かめられる。確かめるのに通信は要らない。

**Why this priority**: ログインとサービストークンが併存する間、どちらが使われるのかが分からないと、案内に従っても直らない場面がある。

**Independent Test**: 未設定、ログイン済み、環境変数にサービストークンがある、の 3 つの状態で状態を表示し、それぞれ正しい方法が示されることを確かめる。

**Acceptance Scenarios**:

1. **Given** ログイン済み, **When** 所有者が状態を表示する, **Then** 方法（ログイン）、管理 API の URL、ログインした日時、アクセストークンの期限が表示され、
   資格情報の値は表示されない。管理 API には接続しない
2. **Given** 環境変数にサービストークンがあり、ログインもしている, **When** 状態を表示する, **Then** 使われるのはサービストークンであることが示される
3. **Given** 何も設定していない, **When** 状態を表示する, **Then** ログインしていないことと、`kumo login` の実行が案内される

---

### Edge Cases

- **ブラウザを開けない**: 開くべき URL を表示して待つ。URL は同じ PC のブラウザで開く必要がある（ログインの結果は、この PC の中でだけ受け取る）。
- **ログインの待ち時間が上限（5 分）を超える、または所有者が中断する**: 資格情報は何も保存せず、もう一度実行するよう案内する。
  この PC の登録は、ログインの前に済んでいれば残す（資格情報ではなく、消せないので作り直さない）。
- **所有者以外のアカウントでログインする**: 入口（Access）がブラウザで拒否する。CLI は何も受け取れないまま、時間切れか中断で終わる。
- **ブラウザでのログインの結果が、CLI が始めたログインと対応しない（別の要求からの応答、拒否やエラーの応答）**: 受け付けず、資格情報を何も保存しない。
- **ログインの結果を受け取る口（この PC の中だけで開く口）を用意できない**: 理由を表示して終わる。
- **管理用のサービスでブラウザでのログイン（Managed OAuth）が有効になっていない、または使えなくなった**: ログインできないことと、サービストークンで
  使い続けられること、手順書の参照先を表示する。
- **アクセストークンの期限が切れた**: ブラウザを開かずに自動で取り直す。期限切れの応答による取り直しは 1 回の要求につき 1 回までとし、繰り返さない。
- **許可の期間が切れた、管理画面や API で取り消された（アプリ単位・ユーザー単位）**: 「`kumo login` を実行してください」と案内する。
- **2 つ以上の CLI が同時にアクセストークンを取り直す**: どれも成功する。保存したログインの記録は壊れない。
- **ログインの記録を保存し直せない（ほかのプログラムが開いているなど）**: 警告して操作は続ける。次の操作は前の記録で取り直す。
- **ログインの記録が壊れている、形式が違う**: 理由を示し、`kumo login` でログインし直すよう案内する。記録の内容（資格情報）は表示しない。
- **管理 API の URL として、ログインした URL と別の URL が指定されている（環境変数など）**: 保存した資格情報を別の URL に送らない。
  食い違っていることと、ログインし直す方法を表示する。
- **別の管理 API の URL でログインし直す**: 前のログインの記録を置き換える。前の許可は取り消す（できなければ警告する）。
- **この PC の登録が使えなくなった（管理用のサービス側で消えたなど）**: ログインのときに 1 回だけ登録し直す。
- **PC をなくした、記録が漏れた**: その PC ではログアウトできない。管理画面か API で、許可をアプリ単位またはユーザー単位で取り消す
  （ほかの PC の許可も消える）。手順は手順書に書く。
- **社内プロキシの内側**: 管理 API との通信は、今と同じくプロキシの設定に従う。ログインの結果は PC の中で受け取るので、プロキシを通らない。
- **ログアウトのときに許可を取り消せない（通信できない）**: 記録は消し、許可が期間まで有効であることと、管理画面や API での取り消し方法を表示する。

## Requirements *(mandatory)*

### Functional Requirements

**ログイン**

- **FR-001**: 所有者は、`kumo login` で、ブラウザで所有者としてログインし、管理操作に使う資格情報をこの PC に保存できなければならない（MUST）。
  サービストークンのシークレットの入力や、設定ファイルの手書きを求めてはならない（MUST NOT）。
- **FR-002**: 管理 API の URL は、コマンドの引数で指定できなければならない（MUST）。省略したときは、環境変数、ログインの記録、設定ファイルの順に探し、
  見つからなければ指定を求めて使い方の誤り（終了コード `2`）で終わらなければならない（MUST）。
- **FR-003**: CLI は既定のブラウザでログインの画面を開かなければならない（MUST）。開けないとき、または所有者が開かないよう指定したときは、
  開くべき URL を表示して待たなければならない（MUST）。
- **FR-004**: ログインの結果は、この PC の中からしか届かない口で受け取らなければならない（MUST）。待つのは最長 5 分とし、時間切れや中断のときは、
  資格情報を何も保存せずに終わらなければならない（MUST）。
- **FR-005**: CLI は、受け取った結果が自分の始めたログインに対応することを確かめ、対応しない結果、拒否、エラーの応答を受け付けてはならない
  （MUST NOT）。受け取る途中の値を第三者に横取りされても、それだけでは資格情報を得られない方法でログインしなければならない（MUST）。
- **FR-006**: この PC の登録は、PC ごとに 1 回だけ行い、以後のログインで使い回さなければならない（MUST）。登録が使えないと分かったときだけ、
  1 回登録し直す。
- **FR-007**: ログインの後、CLI は保存した資格情報で管理 API を呼んで使えることを確かめ、結果を表示しなければならない（MUST）。
- **FR-008**: ログイン済みの状態でログインし直したときは、新しい許可に置き換え、前の許可を取り消さなければならない（MUST）。
  取り消せなかったときは警告する。

**管理操作での利用**

- **FR-009**: 管理操作で使う資格情報は、次の順に選ばなければならない（MUST）。どの資格情報もなければ、`kumo login` の実行を案内して
  使い方の誤り（終了コード `2`）で終わる。
  1. 環境変数のサービストークン: `KUMODANA_CLIENT_ID` と `KUMODANA_CLIENT_SECRET` のどちらか一方でも設定されていれば、この機能の追加前と
     同じ経路（環境変数と設定ファイルを項目ごとに組み合わせる）を使う
  2. ログインの記録
  3. 設定ファイル（`config.json`）のサービストークン
- **FR-010**: CLI は、アクセストークンの期限が近いか切れているとき、また管理 API が資格情報の期限切れを示したときは、ブラウザを開かずに
  アクセストークンを取り直し、操作を続けなければならない（MUST）。期限切れの応答による取り直しとやり直しは、1 回の要求につき 1 回までとする（MUST）。
- **FR-011**: 許可の期間が切れたとき、許可が取り消されたとき、取り直しが拒否されたときは、「`kumo login` を実行してください」と案内し、
  終了コード `1` で終わらなければならない（MUST）。サービストークンを使っているときは、今までどおりサービストークン向けの案内を出す（MUST）。
- **FR-012**: 複数の CLI が同時に取り直しても、どれも失敗してはならず（MUST NOT）、保存したログインの記録が途中の状態で壊れてはならない（MUST NOT）。
- **FR-013**: 保存した資格情報は、ログインした管理 API の URL にだけ送らなければならない（MUST）。別の URL が指定されているときは送らずに、
  食い違いを示して終わらなければならない（MUST）。

**保存と表示**

- **FR-014**: ログインの記録は、設定ファイル（`config.json`）と同じフォルダーの別のファイル（`login.json`）に保存しなければならない（MUST）。
  CLI は `config.json` を書き換えてはならない（MUST NOT）。Windows 以外では、`login.json` を所有者だけが読み書きできる権限（600）に
  しなければならない（MUST）。
- **FR-015**: アクセストークン、リフレッシュトークン、ログインの途中で受け取る値は、どの出力（JSON の出力を含む）やエラーメッセージにも
  表示してはならない（MUST NOT。001 の FR-033 と同じ）。

**ログアウト**

- **FR-016**: 所有者は、`kumo logout` で、この PC の許可を取り消し、保存したアクセストークンとリフレッシュトークンを消せなければならない（MUST）。
  管理 API の URL とこの PC の登録情報は、次のログインのために残す。
- **FR-017**: 許可を取り消せなかったときも、PC の資格情報は消し、取り消せなかったこと、許可が期間まで有効であること、取り消す方法を表示して
  終了コード `1` で終わらなければならない（MUST）。
- **FR-018**: 環境変数にサービストークンがあるときは、ログアウトの後もそれが使われることを警告しなければならない（MUST）。
- **FR-019**: ログインの記録がないときは、その旨を表示して成功（終了コード `0`）で終わらなければならない（MUST）。

**状態の確認**

- **FR-020**: 所有者は、`kumo login --status` で、管理操作に使われる方法（ログイン、環境変数のサービストークン、設定ファイルのサービストークン、なし）と、
  ログインしている場合は管理 API の URL、ログインした日時、アクセストークンの期限を、資格情報の値を表示せずに確かめられなければならない（MUST）。
  この表示では管理 API やログインの仕組みと通信してはならない（MUST NOT）。許可の期限は CLI が受け取れない（#4）ため、ログインした日時を示す。

**既存の経路と運用**

- **FR-021**: 環境変数と設定ファイルのサービストークンは、この機能の追加前と同じように使えなければならない（MUST）。残すか廃止するかは、
  この仕様では決めない（#10）。
- **FR-022**: 管理用のサービス（管理用 Worker）での資格情報の確かめ方（所有者のメールアドレス、CLI のクライアント ID）を変えてはならない（MUST NOT）。
  ログインの経路でも、入口と処理の本体の 2 か所で確かめる（001 の FR-031）。
- **FR-023**: アクセストークンの期間は 15 分（既定）、許可の期間は 1 週間とし、管理画面の選択肢から選んで設定しなければならない（MUST）。
  1 週間が選択肢になければ、1 週間以下でいちばん長い値にする。実際に設定した値と設定の手順は、手順書に残さなければならない（MUST。#9）。

### Key Entities *(include if feature involves data)*

- **ログインの記録**: この PC の `login.json` にだけ保存する。管理 API の URL、この PC の登録情報、アクセストークンとその期限、リフレッシュトークン、
  ログインした日時を持つ。アクセストークンを取り直すたびに書き換わる。ログアウトで資格情報だけが消える。
- **許可**: 管理用のサービスの入口（Access）が持つ。ログインのたびに 1 つでき、許可の期間が過ぎるか、取り消されると使えなくなる。
  PC ごとに別の許可になる。
- **この PC の登録**: ログインを受け付けてもらうために、PC ごとに 1 回だけ作る。管理用のサービス側から消す手段はない（#4）。
- **サービストークン**: 既存の資格情報（001）。この機能では変えない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新しい PC で、CLI のインストールからログインを経て最初の管理操作が成功するまでを、設定ファイルを手で書かずに 3 分以内で行える。
- **SC-002**: 許可の期間（1 週間）内は、アクセストークンの期限（15 分）をまたいでも、管理操作の 100% がブラウザを開かずに成功する。
- **SC-003**: ログアウトが成功した後、その PC に残っていた資格情報で管理操作が成功する割合は 0% である（取り消しはその時点から効く）。
- **SC-004**: アクセストークンとリフレッシュトークンが、どのコマンドの出力（JSON の出力を含む）やエラーに現れる件数は 0 件である。
- **SC-005**: 許可の期間切れと取り消しのとき、100% の場合に「`kumo login` を実行してください」と案内される。
- **SC-006**: 2 つの管理操作を同時に実行してアクセストークンの取り直しが重なっても、失敗は 0 件である。
- **SC-007**: サービストークンでの管理操作は、この機能の追加前と同じく 100% 成功する。管理用のサービス側の資格情報の確かめ方は変わらない。

## Assumptions

- 利用者は所有者 1 人で、主に Windows の PC から使う。macOS と Linux でも動くようにする。
- 所有者は、CLI を使う PC で既定のブラウザを使える。ブラウザのない環境（SSH の先、自動処理）は、サービストークンで使う（残すかどうかは #10）。
- 管理用 Worker の Access アプリでは、ブラウザでのログインの仕組み（Managed OAuth、ベータ）が有効になっている（#4 で有効にした）。
  受け取りの口は PC の中（`127.0.0.1`）だけに限る設定とする。ベータが終わる・変わるなどで使えなくなったときは、サービストークンで使い続ける。
- 許可の期間は、ログインした時点から数え、アクセストークンを取り直しても延びない想定とする。実際の動きは実装中に本番で確かめる（#7）。
- リフレッシュトークンは取り直すたびに変わるが、古いものも許可が続くかぎり使える（#4）。漏れた場合は、許可の期間が切れるか取り消すまで使われうる。
  このため、許可の期間を長くしすぎず、Cloudflare の推奨（アクセストークン 5〜15 分、許可 1〜2 週間）の範囲で短い側の 1 週間にする。
- 取り消すと、その許可のアクセストークンもすぐ使えなくなる（#4）。API でのアプリ単位・ユーザー単位の取り消しも、約 1 分で効く（#4）。
- 所有者の PC のユーザーのプロファイルは、所有者だけが使う。ログインの記録は、OS の資格情報の保管庫ではなく、`login.json` に平文で保存する
  （依存を増やさない）。今 `config.json` に置いているサービストークン（期限 1 年、取り消しは再発行だけ）より、漏れたときの影響は小さい。
- 対象外（今回は作らない）: サービストークンの廃止（#10）、ブラウザのない環境向けのログイン（デバイスコードなど）、複数の管理 API への同時のログイン、
  OS の資格情報の保管庫の利用、Web の管理画面、管理用 Worker の認証の変更。
