# Feature Specification: 共有したリンクの URL を変えずに、置いたファイルの中身を置き換える（kumo put --replace）

**Feature Branch**: `005-replace-content`

**Created**: 2026-11-16

**Status**: Draft

置き換えのエンドポイントを 1 つと `FileSummary.updatedAt` を足し、`kumo put` に `--replace` を足す。配信用 Worker のコード、D1 のスキーマ
（マイグレーション）、リンクとタグの扱いは変えない。

## 背景

- 所有者の要望（2026-11-16）: 一度発行して相手に渡したリンクはそのままにして、リンクが指すファイルの中身だけを新しい内容に差し替えたい。
  共有済みの HTML のガイド（旅行のしおりなど）を直したとき、画像や Markdown 文書を差し替えるとき、誤りを訂正するときに、URL を共有し直さずに
  内容だけを更新する。
- 今の回避策は、新しい内容を置いて新しいリンクを発行し、相手に URL を送り直し、古いリンクを取り消すか古いファイルを消すことだけである
  （論点 11、runbook §10 の「置き直すと別のファイルになる」）。URL が変わり、相手のブックマークやチャットに残った URL は古いままになる。
  リンクのメモとタグは付け直しになり、ファイルの ID と置いた日時も変わる（Issue #26 の「今の回避策と欠点」）。
- 2026-10-19 の 002 の検討では、「キャッシュの削除や `ETag` の意味を変える別の機能」として作らないことにした（論点 11）。Issue #26 で、
  今の作り（`63d3903`）を確かめて方式を比べ、2026-11-16 に所有者が作ることに決めた。

## 用語

- **置き換え**: 棚に置いたファイル（同じ ID）の中身を、新しい内容にすること。ファイルの ID、置いた日時、タグ、リンク（URL、メモ、発行日時、
  取り消しの状態）は変わらない。中身、名前、形式、サイズ、SHA-256 が新しくなる。
- **元の内容 / 新しい内容**: 置き換える前と後のファイルの中身（とその名前、形式、サイズ、SHA-256）。
- **If-Match**: 置き換えの要求に付ける、置き換える前の内容の SHA-256 を二重引用符で囲んだ値（`"<sha256>"`）。配信の `ETag` と同じ形。
- **キャッシュの削除**: 配信用 Worker のエッジのキャッシュを、タグ `f:<id>` で消すこと（001 の contracts/files-rpc.md の `purge`）。

## Clarifications

### Session 2026-11-16（Issue #26 の決定）

- Q: 置き換えの単位 → A: ファイル単位（案 A）。同じ fileId の中身を置き換え、そのファイルのリンクすべてが新しい内容になる。古い内容は残さない
  （憲法 I）。元に戻すときは、手元の原本で置き換え直す。リンク単位の付け替え（案 B）は今回作らない。必要がはっきりしたら別に検討する
- Q: 置き換えで名前と形式が変わってよいか → A: 許可された形式の中なら、ファイル名と形式（`contentType`）を変えてよい。名前は新しい内容のもの
  にする。形式の種類が変わる（画像から HTML など）ときは、CLI が警告する
- Q: CLI の形 → A: `kumo put <path> --replace <id|URL>`。新しいコマンドは作らない。前処理（メタデータの削除、Markdown 文書の変換など）は
  `put` と同じ経路を通す
- Q: 管理 API の形 → A: Issue #26 本文の推奨設計を採る。`PUT /api/files/{id}/content`、`If-Match` は必須、同じ内容が別のファイルとして
  ある場合は 409、`FileSummary` に `updatedAt` を足す、同じ内容での再実行は内容を変えずにキャッシュの削除だけをやり直す、確認の問い合わせ
  （y/N）は出さない

## 採る方式（案 A: 同じファイルの中身を置き換える）

管理用 Worker の `PUT /api/files/{id}/content` が、次の順に処理する。

1. ヘッダー（アップロードと同じもの）と `If-Match` を確かめる。対象のファイルが `ready` でなければ `404 not_found`。
2. 新しい内容が今の内容と同じ（SHA-256 が同じ）なら、何も変えない。リンクを発行したことがあれば、キャッシュの削除だけをやり直し、
   `replaced: false` を返す（下の「同じ内容での再実行」）。
3. `If-Match` が今の SHA-256 と違えば `412 precondition_failed`。
4. 新しい内容が別のファイルとして `ready` であれば `409 duplicate_content`（同じ内容は 1 件だけ。001 の FR-007）。同じ内容のアップロードが
   `pending` で、更新から 10 分以内なら `409 upload_in_progress`。10 分を過ぎたものは片付けて続ける（001 の FR-008 と同じ）。
5. 新しい内容は、今のキーに上書きせず、置き換えのたびに新しく作るキー `files/<id>/<新しい ID>` に置く。既存の上限付きの 1 文
   （`insertPendingWithinQuota`）で、新しい内容の `pending` の行を作る。上限は、元の内容と新しい内容の合計で判定される。R2 に保存し、
   SHA-256 で確かめる。
   - キーを内容のハッシュから作らないのは、元の内容に戻したときに、片付けを待つ古いオブジェクトとキーが重ならないようにするため。
6. D1 の 1 バッチで、ファイルの行の `r2_key`・`name`・`content_type`・`size`・`sha256`・`updated_at` を新しい内容に切り替え、5 の行を、
   元の内容（キー、名前、形式、サイズ、SHA-256）を持つ `deleting` の行にする。
   - 切り替えは、ファイルが `ready` で SHA-256 が `If-Match` のまま、かつ 5 の行が `pending` のまま残っていて、作ってから 10 分たって
     いないときだけ行う。どれかが違えば、何も変えない。10 分を過ぎた `pending` は、同じ内容の置き直しに引き継がれてオブジェクトを
     消されうる（001 の FR-008）ので、切り替えると `ready` の行が実体のないキーを指すおそれがあるため。
   - `r2_key` は UNIQUE なので、元のキーはバッチの中で一時的な値を経て 5 の行へ移す。一時的な値はバッチの外からは見えない。
   - 切り替えなかったときは、5 のオブジェクトと行を消し、今の状態に応じて `404`・`412` を返す。どちらでもなければ（保存に 10 分以上
     かかった）`502 storage_error` を返す。
7. リンクを発行したことがあれば（取り消し済みを含む。削除と同じ条件）、`f:<id>` でキャッシュを 1 回削除する。失敗しても置き換えは完了とし、
   結果（`purge`）を返す。
8. 元の内容のオブジェクトを消してから、その行を消す。7〜8 の途中で止まったときや、消すのに失敗したときは、既存の定期実行が
   `deleting` の行を更新から 15 分で片付ける。6 の前に止まったときは、5 の `pending` の行を 30 分で片付ける。

- 6 の前のどこで失敗しても（上限、保存の失敗、SHA-256 の不一致、途中で止まったものを含む）、ファイルは元の内容のまま配信・取得される。
- `ready` の行の `r2_key` は、切り替えの前も後も、実在するオブジェクトを指す（憲法 III）。
- 元のオブジェクトは、定期実行を待たずに 8 ですぐ消す。使用量がすぐに新しい内容の分だけになり、削除（001 の data-model.md の
  「削除の手順」）と同じ順序になるため。切り替えの直前に D1 を読んだ配信の要求が、消した後に R2 を読むと 404 になりうる（見込み）。
  404 は `no-store` なので、キャッシュには残らない。
- 切り替えの直前に読まれた元の内容が、キャッシュの削除の後にエッジに入るすれ違いは、ありうる（見込み）。取り消しにも同じ種類のすれ違いが
  あり、どちらもエッジの保持（最長 1 時間）が上限になる。

### 同じ内容での再実行

- 新しい内容が今の内容と同じなら、`If-Match` の値にかかわらず、何も変えずに `200`（`replaced: false`）を返し、キャッシュの削除だけを
  やり直す。応答が届かなかった置き換えを、同じ要求のまま（古い `If-Match` のまま）やり直しても、二重に置き換えず、412 にもならない。
  - RFC 9110 §13.1.1 は、要求された変更がすでに反映されているときは、`If-Match` が一致しなくても 2xx で成功を示してよい、としている。
  - 失うものはない。置き換えたい内容が、すでにその内容だからである。
- 名前と形式も変えない（名前だけ違う同じ内容を送っても、名前は変わらない）。

## 管理 API の契約

001 の [contracts/admin-api.md](../001-share-shelf-mvp/contracts/admin-api.md) に追加する。認証、CSRF 対策、共通の応答ヘッダーは 001 のまま。

### `PUT /api/files/{id}/content` — 中身の置き換え（新規）

取得の `GET /api/files/{id}/content` と対になる。

- 本文: 新しい内容そのもの（multipart ではない）
- 必須ヘッダー:
  - `Content-Type`、`Content-Length`、`X-Kumodana-Sha256`、`X-Kumodana-Filename`: `PUT /api/files` と同じ（同じ規則で検証する）
  - `If-Match`: `"<置き換える前の内容の SHA-256>"`（小文字 16 進 64 文字を二重引用符で囲む。`*`、弱い比較の `W/"…"`、複数の値は受け付けない）
- 応答:

| 状態 | 本文 | 意味 |
|---|---|---|
| `200` | `{ "file": FileSummary, "replaced": true, "previous": ContentSummary, "purge": PurgeResult \| null }` | 置き換えた。`previous` は元の内容。`purge` は、リンクを発行したことがなければ `null` |
| `200` | `{ "file": FileSummary, "replaced": false, "previous": ContentSummary, "purge": PurgeResult \| null }` | 今と同じ内容。何も変えず、キャッシュの削除だけをやり直した。`previous` は今の内容と同じ |
| `400 invalid_request` | | ヘッダーの形式が不正。`If-Match` がない・形が違う場合も |
| `404 not_found` | | ファイルがない、または `ready` でない（処理中、削除中） |
| `409 upload_in_progress` | `details: { retryAfterSeconds }`（あるとき） | 同じ内容のアップロードが処理中 |
| `409 duplicate_content` | `details: { fileId }` | 新しい内容が、別のファイル（`fileId`）としてすでにある |
| `411 length_required` | | `Content-Length` がない |
| `412 precondition_failed` | | `If-Match` が今の SHA-256 と違う（ほかの置き換えが先に済んだなど） |
| `413 file_too_large` | | `Content-Length` が上限以上 |
| `413 quota_exceeded` | `details: { usedBytes, limitBytes, requestedBytes }` | 元の内容と新しい内容の合計で、上限を超える |
| `415 unsupported_type` | `details: { allowed }` | 許可されていない形式 |
| `422 checksum_mismatch` | | R2 が内容の不一致を検出した |
| `502 storage_error` | | R2 への保存に失敗した。新しい内容の保存に 10 分以上かかった |

- `200` 以外のどの応答でも、ファイルは元の内容のまま配信・取得される。
- `purge.ok = false` は、配信側のキャッシュに元の内容が最長 1 時間残る可能性があることを示す。同じ要求（または同じ内容の要求）を
  やり直すと、キャッシュの削除だけをやり直す。

```ts
type ContentSummary = { name: string; contentType: string; size: number; sha256: string };
type ReplaceContentResponse = { file: FileSummary; replaced: boolean; previous: ContentSummary; purge: PurgeResult | null };
```

### `FileSummary.updatedAt`（追加）

```ts
type FileSummary = {
  id: string; name: string; contentType: string; size: number; sha256: string;
  createdAt: string; updatedAt: string; tags: string[]; activeLinkCount: number;
};
```

- 今の内容を置いた日時（ISO 8601）。置き換えると、その日時になる。置き換えていないファイルでは、アップロードが終わった日時
  （`pending` から `ready` になった日時）で、`createdAt`（アップロードを始めた日時）とほぼ同じになる。
- D1 の `files.updated_at` をそのまま返す。`ready` の行では、`updated_at` は「今の内容が置かれた日時」を表す（001 の data-model.md の注記）。
- 足すだけなので後方互換である。一覧の並び（`createdAt` の新しい順）は変えない。

### `GET /api/files/{id}/content`（変更）

- R2 のオブジェクトを、`files/<id>` ではなく D1 の `r2_key` で読む。置き換えたファイルの `r2_key` は `files/<id>/<ID>` になるため。
  応答の形は変わらない。

### エラーコード（追加）

`duplicate_content`（409）、`precondition_failed`（412）。

## CLI の契約

002 の [contracts/cli.md](../002-markdown-share/contracts/cli.md) の `kumo put` に、オプションを 1 つ足す。

### `kumo put <path> --replace <id|url> [--keep-exif] [--as <markdown|text>] [--tag <tag>]... [--link] [--label <text>]`

1. 使い方の確認（通信しない）: `<path>` は 1 つだけ。`--replace` の値は、ファイル ID（10 文字）か、リンクの URL かトークン（22 文字。
   URL のクエリ文字列は無視する。`kumo link revoke` と同じ）。ID とトークンは長さと形で見分ける。違反は `invalid_argument`（終了コード `2`）
2. 対象の特定: URL かトークンなら、`GET /api/links?includeRevoked=true` でファイル ID に解決する。見つからなければ `not_found`、
   取り消し済みなら `link_revoked`（どちらも終了コード `1`、何も送らない）。続けて `GET /api/files/{id}` で、今の SHA-256 と
   リンクの一覧を得る
3. 前処理: `kumo put` と同じ（形式の判定、画像と SVG のメタデータの削除、Markdown 文書とテキストの変換、`--keep-exif`、`--as`、警告）。
   原本は読むだけで変えない
4. 同じ内容の確認: 新しい内容が今の内容と違えば、`GET /api/files?sha256=` で別のファイルにないかを確かめ、あれば送らずに `duplicate_content`
5. `PUT /api/files/{id}/content` に、2 の SHA-256 を `If-Match` に付けて送る
6. `--tag` があれば付与し、`--link` があればリンクを発行する（`kumo put` と同じ）

- 確認の問い合わせ（y/N）は出さない（`kumo rm` と同じ。非対話で使えるようにする）。

### 出力（人向け）

```text
<id>  <元の名前> → <新しい名前>  <size>  <形式>  置き換えました
  リンク: <url>  <メモ>
```

- 有効なリンクを、すべて URL とメモで示す（新しい内容が見えるようになったリンク）。取り消し済みのリンクは出さない。有効なリンクがなければ
  `有効なリンクはありません。`
- 今と同じ内容だったとき: `<id>  <name>  <size>  <形式>  内容が同じため、置き換えていません`。キャッシュの削除をやり直して成功したときは
  `（キャッシュの削除だけをやり直しました）` を続ける
- 警告（標準エラー出力）: `kumo put` の警告に加えて、形式の種類が変わったとき（画像・SVG と HTML の間）に
  `形式の種類が変わりました（HTML → 画像）。同じリンクを開いた人には、画像として表示されます。` を出す。PNG から JPEG、Markdown から
  変換した HTML から手書きの HTML などは、種類が同じなので警告しない
- キャッシュの削除に失敗したとき: 置き換えは完了したことと、同じコマンドで削除をやり直せること、やり直さなくても 1 時間以内にすべての
  リンクが新しい内容になることを警告し、終了コード `1` で終わる（`kumo link revoke`・`kumo rm` と同じ）

### 出力（`--json`）

```json
{
  "results": [
    {
      "path": "guide.md", "kind": "markdown", "warnings": [],
      "file": { "…": "FileSummary" }, "replaced": true,
      "previous": { "name": "guide.md.html", "contentType": "text/html; charset=utf-8", "size": 1234, "sha256": "…" },
      "purge": { "ok": true }, "links": [ { "…": "Link" } ]
    }
  ],
  "summary": { "kinds": { "markdown": 1 }, "warnings": 0 }
}
```

- `kumo put` の結果に `replaced`・`previous`・`purge`・`links`（有効なリンク）を足した形。`--link` を付けたときは `link` もある。
  失敗したときは `kumo put` と同じく `error` を持つ。

### エラー（`kumo put` のものに加えて）

| `code` | 条件 | 終了コード |
|---|---|---|
| `invalid_argument` | `--replace` でパスが 2 つ以上、`--replace` の値がファイル ID でもリンクでもない | `2` |
| `not_found` | ファイル ID かリンクが見つからない。置き換えの直前にファイルが削除された | `1` |
| `link_revoked` | 取り消し済みのリンクを指定した | `1` |
| `duplicate_content` | 新しい内容が、別のファイルとしてすでにある（そのファイルの ID を示す） | `1` |
| `precondition_failed` | 対象を確かめてから送るまでの間に、ほかの操作（エージェントの置き換えなど）で内容が変わった | `1` |
| `quota_exceeded` | 元の内容と新しい内容の合計で上限を超える（その旨を案内する） | `1` |
| `network_error` | 応答を受け取れなかった。置き換えが済んだかは分からないので、同じコマンドのやり直しを案内する（済んでいればキャッシュの削除だけになる） | `1` |

## 採らない方式と理由

- **B. リンクの向き先（`fileId`）を新しいファイルへ付け替える**: 古いファイルが棚に残り、「戻せる」ことは旧版を棚に保管することになる
  （憲法 I の「世代管理をしない」と緊張がある）。付け替えを誤ると、非公開のファイルを、そのリンクを持つ人に見せてしまう（憲法 II）。
  リンク単位で別の内容に向けたい需要がはっきりしたら、別に検討する。
- **C. 新しいファイルを置き、リンクとタグを移してから古いファイルを消す（入れ替え）**: ファイルの ID と置いた日時が変わる。アップロードと
  入れ替えが別の要求なので、間で失敗すると新しいファイルが普通のファイルとして残る。
- **R2 の同じキー `files/<id>` に上書きしてから D1 を更新する**: R2 と D1 の更新が 1 つにならない。間で失敗したり、配信の読み取りと
  すれ違ったりすると、配信の `Content-Length`・`ETag`（D1 の値）と本文（R2）が食い違う。
- **`cf r2`・`cf d1` で直接書き換える**: 憲法 III に反する。
- **新しいコマンド `kumo replace <id|URL> <path>`**: `put` の前処理とオプションをそのまま使えるように、`put` のオプションにした（決定 3）。
- **確認の問い合わせ（y/N）**: 非対話（エージェント、スクリプト）で使えるよう出さない。取り違えは、対象と新旧の名前の表示と、
  `If-Match` で防ぐ。

## 憲法との関係

- **I（原本は手元、世代管理をしない）**: 元の内容は残さない（置き換えの後、すぐに消す）。元に戻すときは、手元の原本で置き換え直す。
  CLI は原本を読むだけで、変更しない。
- **II（既定は非公開、共有はリンクで行う）**: リンクの向き先は変えない。リンクを持つ人が見られるのは、今までどおり「そのリンクを発行した
  ファイル」だけで、別の非公開のファイルを見せる経路を作らない。キャッシュの削除に失敗したときは、そのことを利用者に示す。
- **III（書き込み経路は管理 API だけ）**: 書き込みは管理 API だけ。`ready` の行の `r2_key` は、切り替えの前も後も実在するオブジェクトを
  指す。途中で止まった残骸（`pending`・`deleting` の行とオブジェクト）は、既存の定期実行で片付く。配信用 Worker は変えない。
- **IV（多層防御）**: 認証、CSRF 対策、配信のヘッダー（sandbox など）は変えない。置き換えの内容にも `kumo put` と同じ前処理（EXIF・
  メタデータの削除、Markdown 文書の変換）を通す。エージェントのヘルパーから置き換えるときも、004 の FR-011 の規則が及ぶ。
- **V（コストに上限）**: 上限は、処理中の内容（新しい内容）を含めた合計で、既存の 1 文で原子的に判定する。キャッシュの削除は 1 回
  （`f:<id>`）で済み、無料枠の削除回数（1 分あたり 5 回）を使いにくい。SHA-256 の計算と形式の判定は CLI で行う。
- **VI（重要な経路は自動テストで守る）**: 置き換えの成功、失敗、競合、容量、キャッシュの削除、残骸の片付けを、workerd 上のテスト
  （ローカルの D1 と R2）で確かめる。
- **VII（小さく保つ）**: 新しい表、エンティティ、依存ライブラリ、マイグレーションを足さない。エンドポイントが 1 つと、`kumo put` の
  オプションが 1 つ増えるだけ。
- 憲法の改正は要らない。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 共有済みのページを直して、同じ URL で見せる (Priority: P1)

所有者は、相手に渡した HTML のガイドを手元で直し、`kumo put <path> --replace <URL>` を実行する。渡したリンクの URL はそのままで、
リンクを開いた人には新しい内容が表示される。同じファイルの、ほかの相手に渡したリンクも同じく新しい内容になる。

**Why this priority**: 「URL を変えずに中身を置き換える」ことが、この機能の目的そのものである。

**Independent Test**: リンクを 2 本（1 本は取り消し済み）とタグを持つファイルを置き換え、有効なリンクが新しい内容と新しいヘッダーを返し、
取り消し済みのリンクは 404 のままで、ID・置いた日時・タグ・リンクが変わらないことを確かめる。

**Acceptance Scenarios**:

1. **Given** メモ付きのリンクを 2 本（1 本は取り消し済み）とタグを持つファイル, **When** 所有者が新しい内容で置き換える, **Then** 有効な
   リンクは新しい内容を返し、`Content-Type`・`Content-Length`・`ETag`・`Content-Disposition` の名前は新しい内容のものになる。
   取り消し済みのリンクは 404 のまま
2. **Given** 1 と同じ, **When** 置き換えの前後で `GET /api/files/{id}` を比べる, **Then** ファイルの `id`・`createdAt`・`tags`、
   各リンクの `token`・`url`・`label`・`createdAt`・`revokedAt` は変わらず、`updatedAt` は置き換えた日時になる
3. **Given** Markdown 文書の原本, **When** `kumo put note.md --replace <URL>` を実行する, **Then** `kumo put` と同じく HTML に変換した
   ものが送られ、名前は `note.md.html` になる
4. **Given** 位置情報付きの画像, **When** `--replace` で置き換える, **Then** `kumo put` と同じく、メタデータを取り除いたものが送られる
5. **Given** 置き換えたファイル, **When** 所有者が `kumo get <id>` を実行する, **Then** 新しい内容が新しい名前で保存される
6. **Given** HTML のファイル, **When** 画像で置き換える, **Then** 置き換えは行われ、形式の種類が変わったことが警告される

---

### User Story 2 - 取り違えと競合から守る (Priority: P2)

所有者とエージェントが同じファイルを同時に置き換えても、後から来た方が黙って上書きしない。違うファイルの内容や、すでに別のファイルとして
ある内容で置き換えようとしたときも、何も変わらずに理由が示される。

**Why this priority**: 確認の問い合わせを出さないので、誤った置き換えと競合は、仕組みで防ぐ必要がある。

**Independent Test**: `If-Match` が古い要求、別のファイルと同じ内容、`ready` でないファイル、上限を超える置き換えが、それぞれのエラーになり、
何も変わらないことを確かめる。

**Acceptance Scenarios**:

1. **Given** 所有者が対象を確かめた後、エージェントが先に置き換えた, **When** 所有者の置き換えが届く, **Then** `412 precondition_failed` で
   何も変わらず、CLI は「ほかの操作で変わった」ことを示す
2. **Given** 新しい内容が別のファイルとしてある, **When** 置き換えようとする, **Then** `409 duplicate_content` とそのファイルの ID が示され、
   何も変わらない（CLI は送る前に気づく）
3. **Given** 処理中か削除中のファイル, **When** 置き換えようとする, **Then** `404 not_found` で、何も変わらない
4. **Given** 元の内容と新しい内容の合計が上限を超える, **When** 置き換えようとする, **Then** 使用量・上限・要求サイズ付きの
   `413 quota_exceeded` で、何も変わらない
5. **Given** 取り消し済みのリンクの URL, **When** `--replace` に指定する, **Then** `link_revoked` で、何も送らない
6. **Given** 2 つ以上のパス, **When** `--replace` を付けて実行する, **Then** 使い方の誤り（終了コード `2`）で、何も送らない

---

### User Story 3 - キャッシュの削除に失敗しても、置き換えは済み、やり直せる (Priority: P3)

キャッシュの削除に失敗しても置き換えは完了し、所有者にはそのことと、やり直し方が示される。同じコマンドをもう一度実行すると、
内容は変えずにキャッシュの削除だけをやり直す。

**Why this priority**: 削除の回数には無料枠の制限（1 分あたり 5 回）がある。失敗を隠さず、やり直せることが要る（憲法 II）。

**Independent Test**: キャッシュの削除が失敗するようにして置き換え、置き換えが完了して `purge.ok = false` が返り、CLI が終了コード `1` で
やり直し方を示すこと、同じコマンドのやり直しで内容が変わらずに削除だけが行われることを確かめる。

**Acceptance Scenarios**:

1. **Given** リンクを発行したことがあるファイル, **When** 置き換える, **Then** `purge(["f:<id>"])` が 1 回呼ばれる
2. **Given** リンクを発行したことがないファイル, **When** 置き換える, **Then** キャッシュの削除は呼ばれず、`purge` は `null`
3. **Given** キャッシュの削除が失敗する, **When** 置き換える, **Then** 置き換えは完了し、`purge.ok = false` が返り、CLI は同じコマンドで
   やり直せることと、やり直さなくても 1 時間以内に新しい内容になることを示して、終了コード `1` で終わる
4. **Given** 置き換えが済んでいる, **When** 同じ内容でもう一度置き換える（応答を受け取れなかった要求のやり直しを含む）, **Then** 内容は
   変わらず、キャッシュの削除だけをやり直して `replaced: false` が返る

---

### Edge Cases

- **途中で止まる・失敗する（R2 への保存の失敗、`checksum_mismatch`、切り替えの前に Worker が止まる）**: ファイルは元の内容のまま配信・取得
  される。新しい内容の `pending` の行とオブジェクトは、その場で消すか、定期実行が 30 分で片付ける。
- **切り替えの後、元の内容を消す前に止まる**: ファイルは新しい内容になっている。元の内容の `deleting` の行とオブジェクトは、定期実行が
  15 分で片付ける。それまでの間、使用量には元の内容も数える。
- **同じファイルを 2 つが同時に置き換える**: 先に切り替えた方だけが成功し、もう一方は `412` で、何も残さない。
- **置き換えと削除が重なる**: 切り替えの前に削除が始まれば、置き換えは `404` で、新しい内容は消す。切り替えの後なら、削除が新しい内容を消す。
  削除は、ファイルを `deleting` にしてから `r2_key` を読み直すので、読んだ直後に切り替わっても、新しいオブジェクトを消し、元の内容は
  置き換えの残りの行として定期実行で片付く。
- **新しい内容の保存に 10 分以上かかる**（遅い回線で大きいファイルを送るなど）: 切り替えずに `502 storage_error` を返し、新しい内容は消す。
  ファイルは元の内容のまま。
- **元の内容に戻す（A → B → A）**: 手元の原本で置き換え直す。新しい内容には毎回新しいキーを使うので、片付けを待つ古いオブジェクトとは
  重ならない。
- **同じ内容のアップロードが処理中**: `409 upload_in_progress`。10 分を過ぎたものは片付けて置き換える（001 の FR-008 と同じ）。
- **名前だけ違う同じ内容で置き換える**: 内容が同じなので何も変えない（名前も変わらない）。名前を変える手段は、この仕様では作らない。
- **応答を受け取れなかった**: 置き換えが済んだかは分からない。同じコマンドをやり直すと、済んでいなければ置き換え、済んでいればキャッシュの
  削除だけをやり直す。
- **管理用 Worker が古い（デプロイ前）**: 置き換えの要求は `404 not_found` になる。CLI は、直前に削除されたか、管理用 Worker が置き換えに
  対応していない可能性を示す。
- **閲覧者のブラウザに古い内容が残る**: ブラウザの保持（`max-age=60`）の分だけ、最長 1 分残る。キャッシュの削除に失敗したときは、
  エッジに最長 1 時間残る（取り消しと同じ上限）。
- **`ETag` と条件付き要求**: `ETag` は内容の SHA-256 なので、置き換えると変わる。キャッシュの削除に成功していれば、古い `ETag` に `304` が
  返り続けることはない見込み（実地の確認は「受け入れ条件」）。

## Requirements *(mandatory)*

### Functional Requirements

**管理 API**

- **FR-001**: 管理 API は `PUT /api/files/{id}/content` で、`ready` のファイルの中身・名前・形式・サイズ・SHA-256 を新しい内容に
  置き換えなければならない（MUST）。ファイルの ID、置いた日時、タグ、リンク（URL、メモ、発行日時、取り消しの状態）は変えてはならない
  （MUST NOT）。
- **FR-002**: 置き換えの要求には `If-Match: "<置き換える前の SHA-256>"` を必須にし、今の SHA-256 と違えば何も変えずに
  `412 precondition_failed` を返さなければならない（MUST）。ただし、新しい内容が今の内容と同じときは FR-007 に従う。
- **FR-003**: 新しい内容は、置き換えのたびに新しく作るキーに置き、ファイルの行の切り替えと、元の内容を `deleting` の行として残すことを、
  D1 の 1 バッチで行わなければならない（MUST）。切り替えは、ファイルが `ready` で SHA-256 が `If-Match` のままで、新しい内容の `pending` の
  行が作ってから 10 分以内のときだけ行う（MUST）。
- **FR-004**: どの失敗でも、ファイルは元の内容のまま配信・取得できなければならない（MUST）。`ready` の行の `r2_key` には、常に R2 の
  オブジェクトがなければならない（MUST。憲法 III）。残った `pending`・`deleting` の行とオブジェクトは、既存の定期実行で片付かなければ
  ならない（MUST）。
- **FR-005**: 置き換えの間の上限は、元の内容と新しい内容の合計で、既存の 1 文で判定しなければならない（MUST。憲法 V）。超えるときは
  使用量・上限・要求サイズ付きの `413 quota_exceeded` で、何も変えてはならない（MUST NOT）。片付けの後の使用量は、新しい内容の分だけで
  なければならない（MUST）。
- **FR-006**: リンクを発行したことがあるファイルでは、置き換えの後に `f:<id>` でキャッシュを 1 回削除しなければならない（MUST）。
  削除に失敗しても置き換えは完了とし、`purge.ok = false` を返さなければならない（MUST）。発行したことがなければ削除を呼ばず、
  `purge` は `null` にする。
- **FR-007**: 新しい内容が今の内容と同じときは、`If-Match` の値にかかわらず何も変えず、FR-006 のキャッシュの削除だけをやり直して
  `replaced: false` を返さなければならない（MUST）。
- **FR-008**: 新しい内容が別のファイルとしてすでにあるときは、何も変えずに `409 duplicate_content`（`details.fileId`）を返さなければならない
  （MUST。001 の FR-007）。
- **FR-009**: 対象が `ready` でないときは `404 not_found` を返さなければならない（MUST）。
- **FR-010**: `FileSummary` に `updatedAt`（今の内容を置いた日時）を足さなければならない（MUST）。既存の項目は変えてはならない（MUST NOT）。
- **FR-011**: 所有者による取得（`GET /api/files/{id}/content`）は、D1 の `r2_key` で R2 を読み、置き換えた後の内容と名前を返さなければ
  ならない（MUST）。
- **FR-012**: FR-001〜FR-009 と FR-011 には、workerd 上の自動テストを用意しなければならない（MUST。憲法 VI）。

**kumo CLI**

- **FR-013**: 所有者は `kumo put <path> --replace <id|URL>` で、ファイルの中身を置き換えられなければならない（MUST）。新しいコマンドは
  作らない。
- **FR-014**: `--replace` のときも、`kumo put` と同じ前処理（形式の判定、画像と SVG のメタデータの削除、Markdown 文書とテキストの変換、
  `--keep-exif`、`--as`、警告）を通さなければならない（MUST）。原本は変更してはならない（MUST NOT）。
- **FR-015**: 対象は、ファイル ID か、リンクの URL（またはトークン）で指定できなければならない（MUST）。URL は既存の `GET /api/links` で
  ファイル ID に解決し、取り消し済みのリンクは、何も送らずにエラーにしなければならない（MUST）。
- **FR-016**: `--replace` のときのパスは 1 つだけとし、2 つ以上は使い方の誤り（終了コード `2`）にしなければならない（MUST）。
- **FR-017**: CLI は、置き換える前に `GET /api/files/{id}` で今の SHA-256 を取り、`If-Match` に付けなければならない（MUST）。
- **FR-018**: 人向けの出力では、元の名前と新しい名前、サイズ、形式、有効なリンクの URL とメモを示さなければならない（MUST）。形式の種類が
  変わる（画像・SVG と HTML の間）ときは警告しなければならない（MUST）。`--json` の結果には `replaced`・`previous`・`purge` を含めなければ
  ならない（MUST）。
- **FR-019**: キャッシュの削除に失敗したときは、置き換えは完了したことと、同じコマンドでやり直せることを示し、終了コード `1` で終わらなければ
  ならない（MUST）。
- **FR-020**: 確認の問い合わせ（y/N）は出してはならない（MUST NOT）。

**変えないもの**

- **FR-021**: 配信用 Worker（`apps/files`）のコード、D1 のスキーマ、リンクとタグの扱い、`PUT /api/files` の振る舞いは変えてはならない
  （MUST NOT）。

### Key Entities *(include if feature involves data)*

- **ファイル**（001）: 置き換えで、`r2_key`・名前・形式・サイズ・SHA-256・`updated_at` が変わる。ID、`created_at`、状態（`ready`）は
  変わらない。置き換えた後の `r2_key` は `files/<id>/<置き換えのたびに作る ID>`。
- **置き換えの途中の行**: 新しい内容を置く間の `pending` の行（上限の判定と、途中で止まったときの片付けに使う）と、切り替えの後に
  元の内容を持つ `deleting` の行。どちらも一覧や配信には出ず、置き換えの最後か定期実行で消える。新しい表は作らない。
- **リンク**・**タグ**（001）: 変わらない。

## Assumptions

- 利用者は所有者 1 人である。所有者の PC の CLI と、所有者のエージェント（004）が、同じファイルを置き換えることがある。
- エージェントは、004 のヘルパーから `GET /api/files/{id}`（`If-Match` の値を得る）と `PUT /api/files/{id}/content` を呼べば置き換えられる。
